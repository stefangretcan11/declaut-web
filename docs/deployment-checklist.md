# Deployment checks and remaining launch inputs

## Automated checks without provider accounts

[CI](../.github/workflows/ci.yml) runs on pushes and pull requests, with read-only repository permissions and no staging secrets:

1. Install the committed npm lockfile with `npm ci` on Node.js 24.
2. Generate Next.js route types, then run TypeScript checks.
3. Run application tests, including Stripe fixtures and deployment-checker tests.
4. Install PostgreSQL 17 binaries from the official PostgreSQL Apt repository.
5. Run all committed SQL migrations and database behavior tests in a disposable local cluster, as the non-root runner user.
6. Build Next.js for production with no real Supabase, SMTP or Stripe credentials.

The tests start their own local PostgreSQL cluster over a temporary Unix socket and delete it afterward. They do not connect to hosted Supabase. `initdb` must not run as root; only package installation uses `sudo` in CI.

The workflow uses verified official `actions/checkout@v7` and `actions/setup-node@v7` tags. It does not execute repository code through `pull_request_target` or grant write permissions.

## Check an exact deployed origin

Use the URL returned by Vercel or the owner-confirmed stable domain. The checker does not guess project domains and accepts no credentials or protection-bypass secret.

```sh
node scripts/check-deployment.mjs --url=https://YOUR-DEPLOYMENT.vercel.app
```

It requires:

- HTTP 200 HTML for `/`, `/login`, `/preturi`, `/descarcare`, `/intrebari-frecvente` and `/contact`.
- The actual Declaut login form at `/login`.
- HTTP 401, JSON `{"error":{"code":"unauthorized"}}`, and `Cache-Control: no-store` from an unauthenticated `POST /api/license`.
- No redirects. A Vercel Authentication redirect or a generic Vercel 401 is a failure, even though its status resembles the application's auth boundary.

No authorization header is sent, and the unauthenticated license check must return before device registration. This is an availability/authentication-boundary check, not an authenticated license, email or payment test.

For only the home/login/license checks, add `--core-only`. HTTP loopback is allowed only with explicit `--allow-local`, for example:

```sh
node scripts/check-deployment.mjs --url=http://127.0.0.1:3100 --allow-local
```

The same public checks can be run manually with [Check deployment](../.github/workflows/deployment-check.yml) in GitHub Actions. Supply the exact HTTPS origin in the workflow input; no GitHub environment secrets are required.

## Optional staging browser acceptance

[Staging auth acceptance](../.github/workflows/staging-auth.yml) is manual and deliberately restricted to `main`. It never runs on a pull request or a feature-branch dispatch. Ordinary CI remains usable without this workflow.

Before enabling it:

1. Create a GitHub environment named `staging-tests`. Restrict deployment branches to `main`, and configure environment reviewers where the repository's GitHub plan supports them.
2. Put the **staging** values below in that environment's secrets:

```text
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
SUPABASE_SERVICE_ROLE_KEY
LICENSE_PRIVATE_KEY_BASE64
LICENSE_KEY_ID
```

3. Confirm all staging migrations have been applied. The workflow does not push migrations or change remote auth settings.
4. Dispatch the workflow from `main` after review. It builds locally, uses the runner's Chrome, creates temporary staging accounts/tokens, exercises the browser flow and removes its local credential files afterward.

The workflow fixes issuer `declaut-staging` and audience `declaut-desktop`. It verifies the supplied Supabase URL/publishable key and derived signing public key against the distributed staging config before creating fixtures. Its public PEM is derived from the staging signing key in memory; no signing private key file or test artifact is uploaded. If environment-secret features are unavailable for the repository/plan, run `npm run test:auth` locally with the existing ignored staging configuration instead of weakening the workflow's trust boundary.

This uses real Supabase auth tokens generated by the admin API and tests browser sessions plus REST licensing. It does **not** verify actual SMTP inbox delivery. Fixtures are removed by test teardown; if a job is terminated before teardown, inspect Supabase Auth for the matching temporary `auth-browser-` test account before rerunning.

## Deployment sequence

1. Preserve the working Ireland staging Supabase project (`eu-west-1`). Future production also uses Ireland; Vercel backend functions select Dublin (`dub1`) through `vercel.json`.
2. Apply new SQL migrations to staging using the configured GitHub integration or reviewed `supabase db push`; verify migration history. The initial schema and signup-consent migrations are already recorded on staging.
3. Commit and push application changes and the lockfile. In Vercel, deploy the branch/commit that actually contains `package.json`, `vercel.json` and `src/app/`. Redeploying the original README-only commit cannot produce the application.
4. Use the Next.js preset, repository root, Node.js 24, `npm run build` and framework-default output directory. Set `SITE_URL` to the stable staging origin.
5. Put staging Supabase and signing values in the dedicated staging Vercel project's relevant Preview/Production scopes. The Vercel “Production” label belongs to that staging project and does not mean live Declaut billing.
6. Point the owner-confirmed `https://declaut-web.vercel.app` domain at the intended verified deployment. Ensure desktop clients can reach `/api/license` without a Vercel browser login.
7. Run the secret-free deployment checker against the exact URL, then `LICENSE_API_URL=https://YOUR-DEPLOYMENT.vercel.app npm run test:staging` from the configured local checkout for authenticated license acceptance.
8. Share [the Track B handoff](track-b-handoff.md), its public config JSON, and public verification keys only after recording the exact deployed URL and result.

The previously verified license reference was `https://declaut-f7vs3twun-declaut.vercel.app` on 2026-10-24. That historical reference does not prove that the latest frontend or stable domain is ready.
